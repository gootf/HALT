## 1. 目的与设计立场

HALT 把"用 AI Agent 跑长任务"变成**运维一台持久化状态机**。其前提：

> Agent 的上下文窗口是内存（易失），工作区是磁盘（持久）。一切重要状态必须落盘。新会话必须仅凭工作区文件即可完全恢复任务。

HALT 在任务生命周期的每一刻回答六个问题（这一映射是整个规范的脊柱）：

| # | 常设问题 | 由何处回答 |
|---|---|---|
| Q1 | 我处于什么状态？ | 节点生命周期状态 + 日志（02、04） |
| Q2 | 我在什么条件下进入该状态？ | 以日志事件记录的转移守卫（02） |
| Q3 | 已产生哪些不可逆变化？ | 副作用分类 S0–S3 + 回执记录 |
| Q4 | 哪些变化已持久保存？ | 提交规则 + 产物登记（01§5、04） |
| Q5 | 哪些可能丢失？ | 恢复时的未提交尾段检测（05§3） |
| Q6 | 下一步允许做什么？ | Frontier 计算 + 转移函数（02§5） |

因此接续中的 Agent 的 operative 问题**从来不是**"我做到哪了？"，而永远是：

> **"我最后一个可证明稳定的位置在哪里？"**

## 2. 执行模型（公理）

全部 HALT 规则由五条关于 LLM-Agent 执行环境的公理导出。它们是对现实的假设而非愿望——违反它们的方案在实践中失败。

- **AX-1 易失性。** Agent 的工作记忆（会话上下文）可能在任何时刻丢失，没有预警，也没有优雅告别。只有写入工作区的内容幸存。（App 崩溃、配额死亡、手滑关窗，皆属此类。）
- **AX-2 非确定性。** 同一动作重复执行可能产生不同结果（采样、外部服务漂移、时序）。
- **AX-3 自述不可信。** Agent 关于自身或他人行为的陈述（"我做完了 X"、"worker 完成了 Y"）在被工作区或环境验证之前**证据权重为零**。此条适用于 Agent 自己、子代理与人类报告。
- **AX-4 任意点中断。** 中断可能发生在任意两个基本操作之间。除非协议明确使某序列可作为一个单元恢复，否则不存在天然的原子性（INV-3）。
- **AX-5 时变性。** 环境条件（API 配额、模型健康度、失败率）是时段变量。测得的失败率只对其测量窗口有效。（实证：同一模板的 worker 首亡率一小时内从 25% 摆到 75%。）

## 3. 定义

以下定义在所有 HALT 文档中按此唯一含义使用。每个概念恰有一个定义；同义混用即违规。

- **D1 Agent（执行体）。** 通过执行 Action 来推进任务的任意实体：LLM 进程、人类、或以确定角色行动的小组。HALT 规则基于角色而非物种。
- **D2 任务实例（Task Instance）。** 由一次根 SOP 调用管辖的有界事业，唯一 `task_id` 标识，栖身于恰好一个 Workspace。
- **D3 工作区（W）。** 承载一个 Task Instance 全部持久产物的持久目录树。若 W 丢失且无副本，任务按定义不可恢复；因此 W 必须被当作任务的生命对待。
- **D4 任务图（G）。** Task Instance 的 Work Node 有向无环图 `G=(V,E)`，边编码依赖。G 在 INIT 创建，此后只增注、不删除既有结构（历史保全；MAGE 式分支通过节点属性表达，而非改写图）。
- **D5 节点（v∈V）。** 最小可调度工作单元，含：稳定 `node_id`；Spec（目标/输入/验收标准/约束/预算）；依赖；生命周期 State；尝试计数；登记产物。
- **D6 节点 Spec。** 节点的不可变契约："完成"意味着什么。执行开始前写定；只能经显式 AMENDMENT 日志事件变更（绝不静默修改）。
- **D7 动作（Action）。** 运行中节点内 Agent 执行的一个基本步骤：一次工具调用、一次文件写、一次人工操作。
- **D8 副作用（Side Effect）。** 对 Agent 自身头脑之外的任何改变：文件写删、外部服务调用、消息发送。分 S0–S3 四类（见 §6）。
- **D9 日志（Journal, J）。** Task Instance 已提交 Event 的追加式序列。已追加记录**不可变**。更正=新纪录取代旧纪录，绝不改写。日志即黑匣子。
- **D10 事件（Event）。** 一条已提交日志记录：`{seq, tx_id?, ts, actor, kind, payload}`。kind 包括 STATE_TRANSITION、ARTIFACT_REGISTERED、DECISION、AMENDMENT、RECEIPT（外部效果凭证）、NOTE、HEARTBEAT 等。
- **D11 检查点（Checkpoint, K）。** 小而廉价的机器可读指针文档（JSON）：当前 FSM 位置、frontier 摘要、计数器、预算、模式旗标。K 是由 Journal+磁盘再生的**缓存**，绝非真相源（INV-2）。
- **D12 产物（Artifact）。** 任务工作产生的任何文件/内容，登记于产物登记簿：`artifact_id`、路径、产出节点、校验和（或 size+mtime 弱标识）、状态。
- **D13 证据（Evidence）。** 验证者自己取得的关于磁盘或环境的可核验观察：读回校验、目录扫描、checksum、查询结果。与 D14 相对。
- **D14 断言（Claim）。** 关于某事为真或已被完成的口头/书面陈述。未经验证证据权重为零（AX-3）。
- **D15 SOP。** 符合 HALT-03 接口的具名、版本化自动机模块。SOP 是数据（规格），不是某个具身过程：任何持有规格的 Agent 都能执行或恢复它。
- **D16 SOP 实例（Instance）。** 一个 SOP 绑定到某 scope（根任务或父节点）的一次运行期出现，拥有 G 的子图、日志命名空间切片与 Checkpoint 切片。
- **D17 Frontier（可 frontier 的合法工作集合）。** 依赖满足且状态允许启动的节点集合。由任务图计算得出；这是唯一合法的新工作来源。
- **D18 中断（Interruption）。** Agent 操作在任意点的非计划终止（AX-4）：崩溃、会话被杀、预算耗尽、worker 消失、人类关闭应用。
- **D19 恢复（Recovery）。** 使 Task Instance 回到一致状态（存在 Frontier 且至少一个节点可合法启动）的固定程序（05）。
- **D20 记忆库（Memory Store, M）。** 超出单任务生命周期的持久知识库（以稳定 ID 寻址的条目），受 HALT-10 管辖。区别于 Task Instance 自身的产物。
- **D21 决策记录（Decision Record）。** 记录一次抉择的日志事件：考虑过的选项、决定、理由、权威来源（授权/用户裁决/规则引用）。
- **D22 导航输入（Steering Input）。** 执行期间来自人类或上级权威的任何指令。它**必须先立即落盘**（成为日志事件，从而在中断中幸存），然后才被行动（09）。
- **D23 审批门（Approval Gate）。** 附着于特定节点/SOP 特定转移上的显式等待人工裁决的守卫（09）。
- **D24 契约（Contract）。** 交给执行方一段有界工作的完整输入包：节点 Spec + 相关证据指针 + 预算 + 汇报义务（07§4）。

## 4. 四件持久产物

合规的 Task Instance 在其 Workspace 内维护且仅维护以下持久结构（布局见 04）：

1. **任务图** `task-graph.json` —— 节点（D5）及 Spec/依赖/状态/尝试计数的机器可读 DAG。INIT 创建，此后只增。
2. **日志** `journal.jsonl` —— 追加式事件流（D9/D10），每行一个 JSON 对象，seq 单调递增，只增不改。
3. **产物登记簿** `artifacts/registry.json` + `artifacts/` 文件 —— 每个产物带 checksum 类身份登记（D12）；登记与提交同步发生（§5）。
4. **检查点** `checkpoint.json` —— 指针缓存（D11）：FSM 位置、frontier、计数、预算、模式、next_hint。每次提交后整体重写（廉价）；丢了无害（05 可重建）。

**规则 C-ART。** 凡超出琐碎规模的 Task Instance，四者必须齐备，必须都在 W 内。任何任务关键信息不得只存在于会话上下文中。

## 5. 提交规则（微提交协议）

核心操作纪律。每单位进展依序：

```
1. DO      执行一个 Action，产出一个有界输出
2. WRITE   将输出落盘（文件/产物）
3. VERIFY  读回所写内容并与意图比对
           （checksum / size / 抽样内容——按关键性成比例）
4. COMMIT  追加一条日志事件（含 seq、ts、actor、kind、payload 引用）
5. POINT   更新 checkpoint.json（廉价指针刷新；高吞吐循环可按每 N 事件
           或 T 秒批量刷新）
```

- **规则 C-UNIT。** 工作单元必须足够小：(a) 输出能装进一次写调用；(b) 在途丢失最多损失它自己的预算。（实证依据：被要求单步产出大载荷的 worker 倾向于停在推理态而死；微追加协议存活。）
- **规则 C-VERIFY。** 第 3 步用 Evidence，不用"我已经写了"的感觉（AX-3）。喂给下游节点的 S0 输出必须读回；大批低风险数据按比例抽检即可，完整验证留给节点的 VERIFY 阶段（02）。
- **规则 C-TX。** 跨多个事件的逻辑变更共享一个 `tx_id`。恢复时悬空 tx_id 处置为：若能从幸存部分确定性地补完则补完；否则隔离残部并将受影响节点标回 PENDING（绝不静默丢弃）。
- **规则 C-NOREWRITE。** 任何人不得改写日志行或覆盖已登记产物。取代=引用旧物的新事件。失败路径被隔离（挪到一旁并标记），不被抹除——失败经验是资产（MAGE Revise 保留失败分支为兄弟节点）。

**定义（稳定位置）。** Task Instance 的*最后一个可证明稳定位置* = 其所有事件均带已验证 Effect 的最长日志前缀。其后皆为*未提交尾段*：可能丢失，永不可信，留待恢复时检验（Q5）。

## 6. 副作用分类（回答 Q3）

每个 Action 执行前分类：

| 类别 | 性质 | 例 | 纪律 |
|---|---|---|---|
| **S0** | 本地、增量 | W 内新文件；追加 | 全程提交规则覆盖；随时可重做 |
| **S1** | 本地、破坏性 | 覆盖/删除/移动既有产物 | 先备份或隔离（`old/` 副本+登记备注）再动手；永远存在还原路径 |
| **S2** | 外部、可重放 | 只读查询、搜索、幂等拉取 | 自由执行；结果记为事件；重做廉价安全 |
| **S3** | 外部、不可重放 | 发消息、一次性购买、公开发布、通知人类 | 必须过审批门，或在设计上消除；若执行：先取 RECEIPT 凭证（ID/截图/hash）并记日志，方可继续 |

**规则 C-S3。** 合规设计最小化 S3 面。缺少凭证路径的 S3 动作即违规。中断落在"S3 已执行、RECEIPT 未捕获"之间的情形，恢复时按*疑似已发生但不可验证*处理，上呈人工裁决（05§6）。

## 7. 真相层级

来源冲突时，低位胜出：

```
1. 直接证据          （验证者自己的读回 / 盘面扫描 / checksum）
2. 已登记产物        （登记簿与实际文件互证）
3. 日志事件          （已提交记录）
4. 检查点            （指针缓存）
5. 摘要              （进度文档、状态报告、派发文本）
6. 断言              （任何 Agent 或人类的未经验证的说法）
```

**规则 C-TRUTH。** 冲突消解永远沿此阶梯行走。"盘面裁决"是常设决胜规则：对"工作是否发生过"存疑时，查工作区，而不是查任何人（含自己）的记忆或汇报。（实战反复验证：worker 的完成声明屡次被盘扫证伪；反过来，被判"全灭"的工作也多次在盘上完好找回。）

## 8. 不变量

十条不变量是 HALT 的规范性脊柱，其余一切规则都为了维护其中一条或多条。

- **INV-1 持久性。** 每次提交后，Task Instance 的状态仅凭 W 即可完全重构。任何程序不得依赖仅存在于某个会话上下文中的信息。
- **INV-2 单一真相源。** Journal+已登记产物是权威。checkpoint、摘要、报告皆缓存/视图。checkpoint 与 journal 冲突时 checkpoint 输。
- **INV-3 可恢复单元。** 每个多步逻辑变更要么 (a) 归约为提交规则下的逐步提交，要么 (b) 包进 tx_id 且恢复程序知道如何处置其悬空态（确定性补完，否则隔离）。不存在第三种。
- **INV-4 单调历史。** 已完成的工作绝不静默倒退。ID 永久。失败与更正都是新纪录；历史只增。进展可以*分支*，不可以*隐形回卷*。
- **INV-5 幂等续接。** 从任何稳定位置重新驱动 Frontier 必须收敛到同一目标，无论此前多少次尝试死在任何位置。机制：skip-by-evidence——重做某单元前先检查其输出是否已存在且可验证（旗标、checksum、登记簿）。
- **INV-6 证据门控推进。** 节点跨越任何需要验证的转移，只能依据*生产者以外*的实体产出的 Evidence（执行者≠检查者；02§4、08）。
- **INV-7 有界上下文。** 每次 Agent 激活消耗有界输入：契约（节点 Spec+所指证据），绝非全量历史。细节在段落边界压缩、按需展开（HiAgent 模式）。Spec 装不进执行者预算的节点必须继续分解——这是分解错误，不是执行错误。
- **INV-8 失败封装。** 失败的子级（子 SOP 实例、worker、子任务）留给父级的状态是一致的：父级看到良定义的子终态+已登记的部分产出——绝无损坏，绝无沉默。父级决定重试/重划/上报（06§5）。
- **INV-9 可审计。** 对任何当前状态，存在一条日志走查能解释系统如何走到这里：谁、何时、凭何证据、经何授权。后果重大的决策有决策记录（D21）。
- **INV-10 最小权限。** 写权限按角色划分（08）：如审计者对受保护产物只读；worker 只写自己的 scope；只有协调者能改任务图结构。无写权限实体验出的验证结论仍然只是断言——但它们无法腐蚀状态。

## 9. 合规层级

并非所有事业都需要全套仪仗。HALT 定义三级；INIT 时选定并记入 checkpoint。

- **Tier 0 琐碎。** 单会话、低价值、从头重来可接受。可省略 journal/checkpoint。退出条件：预期时长 >1 会话或价值超过随手级别 ⇒ 升 Tier 1。
- **Tier 1 标准。** 四件套齐备+提交规则+副作用纪律+标准恢复。多会话任务默认档。
- **Tier 2 关键/机队。** Tier 1 之上加：多产物变更强制 tx_id 分组；全部 S2/S3 都要回执（不再只是 S3 不可重放类）；周期性审计走查（每 K 次提交或 T 墙钟）；journal 双写（主+镜像逐提交批刷盘）以抗恶劣环境。
